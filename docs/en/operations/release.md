# Release acceptance

pyproject.toml is the version authority. Check it with `python scripts/release/version.py --check` and check generated interfaces with `python scripts/ci/generate_interfaces.py --check`. Preserve exact reviewed file inventories.

Build source/wheel artifacts from the exact commit with build_release.py. Maintainers fetch pinned Python/core inputs with fetch_portable_inputs.py and prepare the locked CPython 3.12 manylinux2014_x86_64 Textual wheelhouse. build_portable_bundle.py reads local inputs only and emits a complete bundle/checksum with licenses and upstream core source links. portable-runtime.json pins the interpreter.

Both Ubuntu 22.04 and 24.04 must pass regressions, real-core tests, legacy installation/migration and complete bundle acceptance. Run verify_portable_bundle.py with --real-users --require-isolation --ssh-user USER as root inside disposable `unshare --mount --net` namespaces, using an existing unprivileged account. Its two unprivileged UID workers verify concurrent isolated instances, authentication, selection persistence, real SSH/PTY Unicode input, keyboard and resize, refusal to update an open UI, installation/update without system Python on PATH, and absence of historical copies. Reports include bundle/installed size, startup time and UI RSS. No accounts or existing services are modified.

The release gate checks both systems' portable reports and the same bundle SHA256. Worktree artifacts are publishable:false development outputs. Retain business/security regressions; replace historical rollback expectations with current-only retention and failed-operation recovery.

## Publish the validated commit

1. Review all current Chinese/English documents and mark old release notes as historical. Set pyproject.toml, run `python scripts/release/version.py --sync`, update the Changelog and stable-version markers, then check versions, documentation, generated references and the exact source inventory. Commit the component license notices as well as the runtime/build changes.
2. Push the reviewed commit and require all jobs of `.github/workflows/test.yml` to pass, including `release-gate`. Both Ubuntu jobs must test the same source commit. Do not use worktree packages or substitute locally rebuilt assets after acceptance.
3. Download `release-candidate-ubuntu-22.04`, `release-candidate-ubuntu-24.04`, both `validation-ubuntu-*` artifacts and `release-gate`. Select the normal source/wheel and portable assets from Ubuntu 22.04 and the corresponding offline kit from each Ubuntu target. Verify the selected normal hashes against `build-receipt.json`, each kit/checksum pair, the gate commit/version and its exact asset inventory. Reject duplicate, missing or mismatched assets.
4. Assemble `validation-evidence.json` from the two validation directories with their unchanged JSON reports. Publish that evidence, `release-gate.json` and exactly the assets listed by the gate. The release tag must resolve to the validated full commit. Describe the current-only retention change, source-to-bundle migration, supported targets and component licenses in the release notes. Mark the new stable release as latest only after all mandatory checks pass.
5. Query the published release and tag, download the delivered checksums/metadata and complete bundle, compare hashes to the gated assets, and check release discovery. Record the release URL and CI run URL. Do not overwrite an earlier version's tag or assets.

The full bundle has its own `.tar.gz.sha256`; `SHA256SUMS` covers the normal source/wheel assets only. Each legacy offline kit has a separate `.sha256`. The build receipt binds source/wheel hashes to a commit, and `release-gate.json` records the accepted asset names. Colocated metadata and checksums are not independent signatures.
